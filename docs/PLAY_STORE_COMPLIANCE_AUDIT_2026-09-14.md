# Seller Terminal Google Play compliance audit

Date: 14 September 2026. Verdict: **not ready to certify for submission**.

This is the requested issue-list option: no application or backend behavior was changed. The working tree already contains substantial uncommitted development. Findings apply to that working tree, not necessarily the version currently on Google Play. No Play Console access, authenticated device walkthrough, live purchases, or deletion requests were used.

## Method and evidence

Reviewed the [requested playbook](https://github.com/mjmirza/app-store-compliance) at commit `05c8f412bd6652c14d10ccaf216c1a931bacaa98`, including its Google Play rejection map and pre-submission checklist, and ran its standalone guard. Checked findings against current Google documentation and actual Flutter/backend code. Terminal base commit: `7a12379f1e1ee051449c2608c9e891ebf2efff51` (dirty).

The guard returned 6 critical, 8 high and 6 medium flags across Android, iOS and web. Those totals are NOT confirmed Play violations: its platform detection includes Flutter's other targets and several checks are keyword heuristics. No skill or submission hook was installed.

## Release and Console checks still outstanding

These are unknowns, not claims that the current declarations are wrong:

- **Data safety:** inventory account identifiers, CRM contacts, shop/customer/staff records, purchases/payment information, selected photos/files, shop location, diagnostics and push identifiers. Assess collection/sharing and exemptions per SDK and data flow. `CrashlyticsService.init()` explicitly enables collection in release, despite the manifest default being false. Do not declare “no diagnostics collected” based on the manifest alone.
- **App access:** supply a stable reviewer seller account and instructions that avoid OTP, funding or location obstacles. Exercise login, offline sale/sync, printing permission denial, registration and every enabled paid/AI feature on release builds.
- **Store listing:** verify title, screenshots, privacy/deletion URLs, content rating, target audience, ads declaration, support details and any AI listing-asset declaration shown in Console. No exported listing/Data safety metadata was located in the Terminal source tree.
- **Financial features:** classify Sanaa Wallet, top-ups and BNPL accurately in the financial-features declaration; verify provider/business requirements applicable to enabled services and distribution countries. A POS alone is not proof that banking/lending rules apply.
- **Account readiness:** confirm verification/package registration, current agreements, account-specific policy notices, and production access. The 12-testers/14-days gate is conditional on the developer account; source code cannot establish completion.
- **Regions:** country availability was not supplied. The playbook emits global/EU/US/other-country deadlines automatically; those are not established obligations for this Uganda-focused app. Verify relevant Console deadlines and distribution scope before treating them as release blockers.
- **Fresh release artifact:** build the exact intended source revision, inspect the AAB manifest and native libraries, validate bundle/APK alignment, and test a Play-generated install on a 16 KB device. Existing build output cannot certify the dirty working tree.

## Checks that already look correct, with limits

- Existing merged release manifest has `targetSdkVersion=36`, `minSdkVersion=24`, version `2.0.5` / `2030`. API 36 meets the [current new-app/update target requirement](https://developer.android.com/google/play/requirements/target-sdk). The Gradle configuration delegates this to Flutter; inspect every actual release rather than assuming CI uses the same SDK.
- Existing `build/app/outputs/bundle/release/app-release.aab` is dated 21 August 2026. Its SHA-256 is `b37c03b37852a9f41e20f2248c6e91ef2a5fb9c4a17cbcefb8d7924ed93c1a80`. All 14 arm64/x86_64 native libraries inspected have ELF LOAD alignment at least 16 KB. ZIP alignment and device execution remain untested. See [Android's 16 KB verification procedure](https://developer.android.com/guide/practices/page-sizes).
- Source and existing merged release manifests exclude broad photo/video read permissions and advertising-ID permissions. No SMS/call-log, all-files, background-location or AccessibilityService permission was found in the inspected merged manifest. Sending marketing SMS through the backend does not itself require Android SEND_SMS.
- Contact-upload explanations and opt-in controls already exist in Settings and the contacts banner. The guard's blanket “no disclosure” finding is not accurate; verify every entry point in a device walkthrough.
- Privacy and deletion URLs both returned HTTP 200 without authentication. No production deletion request was submitted.
- Cleartext traffic and automatic backup are disabled in the manifest. Tokens use `FlutterSecureStorage`; offline password/PIN verifiers use salted PBKDF2 in that secure storage. The scanner's SharedPreferences match is insufficient evidence of plaintext credentials.
- Android HTTPS App Links are declared with auto-verification. Domain/signing association was not tested; the generic custom-scheme scanner flag is not proof the Android links are unsafe.

## Scope of validation

This audit used source inspection, the third-party static guard, public HTTP GETs and read-only ELF inspection. No application changes were made, so Flutter tests/code generation were not run. No build was uploaded and no store approval is claimed. Fix and verify the high-priority items above before requesting release sign-off.
